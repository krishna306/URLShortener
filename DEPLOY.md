# Deploying URL Shortner Z for free

| Piece | Host | Free limit |
|---|---|---|
| gateway, url-service, analytics-service | Render web services (Docker) | Sleep after 15 min idle; ~1 min to wake; 750 instance-hours/month shared by all three |
| frontend | Render static site | Never sleeps |
| Postgres (2 databases) | Neon | 1 GB per project; scales to zero when idle (~1s to wake) |
| Redis | Upstash | 500K commands/month, ~256 MB |

All four Render services are defined in [`render.yaml`](render.yaml).

## 1. Push the repo to GitHub

Render deploys from a Git repo. `.gitignore` keeps every `.env` file out.
Create an empty repo on github.com first, then run:

```bash
git add .
git commit -m "URL Shortner Z"
git branch -M main
git remote add origin https://github.com/<you>/<repo>.git
git push -u origin main
```

## 2. Neon (Postgres)

1. Create a project at neon.tech.
2. In **Databases**, create two databases: `url_service` and `analytics_service`.
3. Click **Connect**, turn **Connection pooling off**, then copy the connection string
   once per database. Prisma migrations need the direct (non-`-pooler`) host.
   Each should look like:
   `postgresql://<user>:<password>@ep-xxxx.<region>.aws.neon.tech/url_service?sslmode=require`

## 3. Upstash (Redis)

1. Create a Redis database at upstash.com, picking the region closest to your Render region.
2. Copy the **TCP** connection URL. It starts with `rediss://` (two s's means TLS).

## 4. Render

1. Go to Dashboard → **New** → **Blueprint**, then pick your GitHub repo.
2. Render reads `render.yaml` and asks for each `sync: false` value:

| Service | Key | Value |
|---|---|---|
| urlz-url-service | `DATABASE_URL` | Neon `url_service` string |
| urlz-analytics | `DATABASE_URL` | Neon `analytics_service` string |
| all three backend services | `REDIS_URL` | Upstash `rediss://` URL |
| urlz-gateway | `URL_SERVICE_URL` | `https://urlz-url-service.onrender.com` |
| urlz-gateway | `ANALYTICS_SERVICE_URL` | `https://urlz-analytics.onrender.com` |
| urlz-frontend | `VITE_API_BASE_URL` | `https://urlz-gateway.onrender.com` |

   `INTERNAL_TOKEN` is generated by Render and copied to the gateway automatically.

3. Click **Apply**. The first build takes a few minutes.

### If a URL is different

If a service name is already taken on Render, it gets a suffix
(e.g. `urlz-gateway-k3x9.onrender.com`). Check each service's real URL in the dashboard.
If one differs from what you typed, fix the env var:

- Gateway URLs: edit them on **urlz-gateway**, and it restarts.
- `VITE_API_BASE_URL`: edit it on **urlz-frontend**, then run **Manual Deploy**.
  Vite bakes this value into the JS at **build** time, so a restart isn't enough.

## 5. Check it

```bash
GW=https://urlz-gateway.onrender.com
curl $GW/health
curl -X POST $GW/api/shorten -H 'Content-Type: application/json' -d '{"longUrl":"https://example.com"}'
curl -i $GW/<shortCode>
curl $GW/api/urls/<shortCode>/stats
```

The first request after idle can take 1–2 minutes: the gateway wakes, then on a cache miss
it wakes url-service too. Later requests are fast.

## How the code handles sleeping services

- **Click events use a Redis Stream, not pub/sub.** While analytics-service sleeps, events
  wait in `stream:clicks`. When a stats request wakes it, it reads the backlog before
  answering. Pub/sub would have dropped them.
- **`/internal/*` needs a shared secret.** Free Render services are all public, so
  url-service rejects resolve calls without the gateway's `x-internal-token` (401).
- **Click counters survive database hiccups.** If the Postgres write fails (e.g. Neon is
  waking up), the flusher puts the count back in Redis and retries on the next flush.

## Upstash command budget

Each redirect uses 3 commands (GET, INCR, XADD), so 500K/month is roughly 150K redirects.
The flusher (every 60s) and analytics drain (every 30s) only use commands while their
service is awake.
